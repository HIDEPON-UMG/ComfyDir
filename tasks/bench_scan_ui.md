## 作業定義

- 目的：変更前と変更後を同じ手順で測り、改善の大きさと、残った問題を、受け取る人が判断できる形で残す。
- 完了条件：結論・比較表・条件ごとの合否・未達の原因・お願いが、この 1 ファイルに書かれている。数値が測定の出力（JSON と判定の命令の表示）に一致する。
- 検証方法：`bench_startup.py judge`（工程 5 の確かめの命令）の出力と、この表の数値の照合。
- 完了条件の変更の記録：2026-11-09 判定の条件 5 を「1 クリック 100 ms 以下」から「変更前の 5 分の 1 以下」に変えた。理由：実測で約 245 ms（変更前 2,470 ms の約 10 分の 1）が今の設計の限界と分かり、利用者が計画の判断 3 で、この受け入れと、仮想スクロールを別の計画に回すことを承認したため。

## 結論

- **判定は 7 条件すべて合格**です（最終の再測定。条件 5 は上の変更後の基準）。
- **起動時スキャン**：約 53.5 分（外挿）から、全ファイルが登録済みの再起動で **2.4 秒**になりました。未登録のファイルが 340 件あるコピーの初回起動でも 83.8 秒です。新規と変更だけを処理し、サイズと更新日時が同じ 14,063 件（100%）を読み飛ばしました。削除は 0 件、旧方式と新方式の列挙差は 0 件です。
- **1 クリック**：2,470 ms から **233 ms**（約 10 分の 1）になりました。当初の基準「100 ms 以下」には届きませんが、利用者が判断 3 で受け入れました。100 ms に近づける案（仮想スクロール）は別の計画の候補として残します。

## 判断 3：1 クリックの基準（承認済み）

- **決定（2026-11-09、利用者の承認）**：約 245 ms を受け入れ、条件 5 を「変更前の 5 分の 1 以下」に読み替えて工程 6 に進む。100 ms を目指す仮想スクロールは別の計画の候補とする。
- **未達だった原因はタイルの数そのものです。** アプリの処理を介さず、クラスを付け外しするだけでも約 290 ms かかります。タイルを先頭 400 枚に減らすと 26 ms でした。13.5k 枚のタイルをブラウザが描くコストです。
- 差し込んだ CSS での切り分け（リポジトリは変更していません）：

  | 条件（クラス付け外しから 2 フレーム目まで） | 中央値 |
  |---|---|
  | 基準 | 199 ms |
  | `transition` を外す | 233 ms（改善なし） |
  | `container-type` を外す | 185 ms（ほぼ改善なし） |
  | `.tile` に `contain: layout style paint` | 100.5 ms |
  | `.tile` に `content-visibility: auto` | 110.7 ms |

- 測定は、同じ機械で ComfyUI などが動いているため揺れます（基準が 199〜290 ms）。
- 採らなかった案：`.tile` に `contain: layout style paint` を足す案（約 100 ms の見通しだが、基準に 0.5 ms 届かず、はみ出す枠線や影を切る恐れの確認が要る）。タイルを画面に見える分だけ作る仮想スクロール（約 26 ms の見込み。約 60〜110 分、既存の動作を壊す危険が高い）。

## 列挙差 1 件（最終の 1 回目）は一時的でした

- 最終の 1 回目の測定で `enum_diff_count` が 1 になりました。直後に読み取りだけで同じ比較を 2 回行い、2 回とも 0 でした。コールドの測定と、その前のウォームの測定でも 0 でした。**最終の再測定でも 0 でした。**
- 生成画像が測定中に増え続けています（登録件数は 13,715 → 14,060 → 14,062 → 14,063 件）。旧方式の列挙と新方式の列挙は時間差で行われるので、その間に増えた 1 件が差として出たと判断します。ずれたパスは記録されておらず、この判断は状況証拠によるものです（再測定の 0 件が裏づけです）。
- 方式の違い（パスの文字列の形）は、単体テストと 4 回の 0 件で否定されています。

## その他の注意点

- **最初の描画と全タイルのトレードオフ**：最初の画面は早く出ますが（1,420 → 844〜1,126 ms）、全タイルがそろうまでは遅くなりました（2,539 → 4,492〜5,186 ms）。先頭 400 枚を先に描き、残りを続けて追加するためです。計画のとおりの動作です。
- **全タイル待ちの時間切れ（コールドの測定）**：ウォームの測定では 3 回とも測れたので、スキャン中に登録件数が増え続けたことが原因と疑っていますが、確かめていません。
- **本番のデータベースの更新日時**：変更前の測定とコールドの測定の前後で、更新日時が変わりました（サイズは同じ）。最終の測定（1 回目と再測定）の前後では変わっていません。本番のデータベースの `scanned_at` の最大値は 04:26:33.677 で、更新日時 04:26:33.684 と 8 ミリ秒の差で一致します。測定ツールは本番のデータベースを読み取り専用で開くので、書いたのは本番サーバー自身の登録処理（増えている生成画像の登録）と考えます。ただし、測定の実行中と重なった理由は説明できていません。
- **変更前の判断（分岐点 1）**：スキャン中でも一覧は 0.30 秒、縮小画像は 5.5 ミリ秒と速く、「スキャンが表示を遅くしている」という根の原因の主張は、この測定では支えられません。計画は「止まって報告し、計画を取り直す」と定めていますが、直ちに実装するというご指示を優先し、推奨の計画を変えずに続けました。「表示まで 1 時間以上」という体験そのものは、再現できていません。
- **タグの見た目の直し**：最初の実装（行内の並び）では、複数語のタグ（`year 2025` など）が行の途中で折り返され、チップが割れました。工程 3 を開き直し、`.prompt-token` を `inline-block` にして直しました（テスト 11 件）。直した後の画面と、コピー文字列（「, 」入り・改行なし）を確認しています。
- 画面の画像（作業用の一時フォルダ。消える可能性があります）：変更前 `…\scratchpad\cio_bench\before_shots\{grid,tags}.png`、変更後（最終）`…\scratchpad\cio_bench\after_shots\{grid,tags}.png`、折り返し修正前 `…\after_warm_before_tagfix_shots\`、コールド `…\after_cold_shots\`。
